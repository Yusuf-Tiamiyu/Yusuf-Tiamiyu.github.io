The problem I walked into

Cerba Lancet Nigeria runs multiple diagnostic lab sites across Lagos. Every week, managers needed one specific answer: are we hitting the 90% TAT target? Which sites are struggling? But the answer was buried in Excel files being emailed back and forth between sites.

By the time someone stitched the spreadsheets together and made sense of the numbers, the week was already gone. Slow sites stayed slow because no one saw the pattern early enough to act on it.

Before this existed, getting a network-wide view of lab performance meant calling each site individually, collecting spreadsheets, and assembling everything manually. Every single week. No one had time. So it often didn't happen.
2

Why I built it the way I did

I could have built a smarter spreadsheet. But smarter spreadsheets still require someone to know how to run them. The real problem wasn't the data — it was the friction between the data and the people who needed it.

So I built an upload-to-dashboard pipeline. Staff drop their weekly Excel file into the app. It gets parsed, pushed into a persistent MySQL database, and immediately surfaces as charts and KPIs anyone can see in a browser. No email chains. No waiting. No analyst in the middle.

The key design decision was making it usable by people who aren't analysts. One upload, everything updates. That constraint shaped everything — from the validation logic to how errors surface to the user.
3

What it changed

Real-time visibility across the network. Sites below 90% TAT show up immediately — not after someone's had time to notice and report it. Lab managers can spot week-over-week trends without touching a spreadsheet.

This is live in production right now. Real data. Real users. It runs on Railway with a persistent MySQL instance — always on, no manual updates needed. That's the bar I hold myself to: build it so it runs without me.
1

Upload & validate

Staff upload the weekly Excel report through the app. pandas reads it, validates column structure, and rejects malformed files before anything touches the database. Bad data doesn't get a chance to corrupt the historical record — it fails loudly with a clear message instead.

2

Persist to MySQL

Parsed rows write via SQLAlchemy. Each upload inserts new weekly records per site and department — nothing overwrites the existing data. The full history accumulates. This is what makes trend tracking possible, not just point-in-time snapshots. The database grows every week without anyone thinking about it.

3

Serve the dashboard

Flask routes query the database and serve an interactive dashboard with Chart.js. TAT% per site vs the 90% target, week-over-week trends, department breakdowns — all in one view that refreshes on every upload.

How I found the problem

The procurement team was managing 1,578 consumable items — gloves, reagents, blood collection tubes — with no central system. Things would run out mid-month. Staff would find out when they went to use something and it wasn't there.

There was no early warning. No visibility into what was running low until it was already a problem. In a lab environment, that's not just inconvenient — it can directly affect patient care. A test can't run without the right reagent. A sample can't be collected without the right tube.

When the tracker first ran, it flagged 1,413 of 1,578 items as below reorder level. 55% had zero stock at all. That was a very interesting morning for the procurement team — and it confirmed that the problem wasn't small.
2

Why I kept it simple on purpose

A lot of Excel tools fail not because they're wrong, but because they're too complex. You update one cell and three other things break. Someone goes on leave and no one else knows how to use it. So it gets abandoned.

The goal here was: set the rules once, then let the spreadsheet do the work every single time. Update the quantity, the status auto-updates. No expertise required after setup. Any team member can pick it up on day one.

3

The hidden insight nobody asked for

The obvious finding was the 89% crisis rate. But the tracker surfaced something less obvious: while the majority of items were critically low, several others were massively overstocked — tying up capital for 35+ months of supply with no plan for it.

It's not just about what's running out. It's also about what's piling up where it shouldn't be. The same system that catches the shortage also catches the waste. That's why building for the full picture matters.
Three formulas, consistently applied across 1,578 rows. Simplicity is a feature — not a shortcut.
1

The 2-month rule

Reorder Level = 2 × average monthly usage. So when the tracker flags REORDER NOW, you still have two full months of stock left. That gap is deliberate — procurement cycles in healthcare aren't fast, and running out is not an acceptable outcome.

2

Status formula

=IF(C2<=D2,"REORDER NOW","OK")

If current quantity ≤ reorder level, flag it. Simple — but applied at scale with conditional formatting, it turns a spreadsheet into a live alert board that anyone can read at a glance.
3

Months remaining

=IFERROR(C2/H2, 0)

Current quantity ÷ average monthly usage. IFERROR handles items with zero usage — no divide-by-zero errors, no broken cells, no one calling me to ask why column G shows #DIV/0!.

This Kaggle dataset covers tech layoffs from March 2020 to early 2023 — the full post-COVID arc. Hiring booms driven by pandemic-era growth, then mass corrections when the numbers stopped adding up. I wanted to see what was actually happening underneath all the headlines.

But the data was a mess. Inconsistent date formats. Blank industry fields that should have been populated. Duplicates — some subtle enough to look like separate events. Trailing punctuation in country names. You can't trust any trend you find in data like this until the data earns that trust. So I cleaned it first. Always.

Then I went in without a fixed hypothesis. I started pulling threads — which companies collapsed entirely? Which years were worst? Was it random, or did the funding stage matter? Let the data lead and document the thinking, not just the answers.

Running analysis on dirty data gives you confidently wrong answers — which is worse than no answer at all. Cleaning isn't the unglamorous part. It's the part that makes everything else valid.
The most telling single fact in this dataset: Quibi raised $2 billion and laid off 100% of its workforce. One of 116 companies that went completely to zero.

Rule one: never touch the original data. Always create a staging table first — it's saved me more than once.
1

Staging table

Working directly on source data means one bad query can permanently alter something you can't recover. The staging table is free insurance — always use it.

Setup
CREATE TABLE layoffs_staging LIKE layoffs;
INSERT INTO layoffs_staging SELECT * FROM layoffs;
2

Duplicate removal with ROW_NUMBER()

Some duplicates are obvious. Others share every field value — you can't tell them apart without using ROW_NUMBER() to assign a sequence and then filter on anything beyond 1.

Deduplication
WITH dedup AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY company, location, industry,
    total_laid_off, percentage_laid_off, `date`,
    stage, country, funds_raised_millions
    ORDER BY company) AS row_num
  FROM layoffs_staging
)
DELETE FROM layoffs_staging2 WHERE row_num > 1;
3

Top 3 companies per year — DENSE_RANK + double CTE

This query stacks two CTEs. The first aggregates layoffs by company per year. The second ranks them within each year using DENSE_RANK(). Then the outer query filters to rank ≤ 3. It's a pattern worth learning — it shows up constantly in real analysis work.

Year-by-year ranking
WITH Company_Year AS (
  SELECT company, YEAR(`date`) AS yr,
    SUM(total_laid_off) AS total
  FROM layoffs_staging2
  GROUP BY company, yr
),
Ranked AS (
  SELECT *,
    DENSE_RANK() OVER (
      PARTITION BY yr
      ORDER BY total DESC) AS ranking
  FROM Company_Year
)
SELECT * FROM Ranked
WHERE ranking <= 3 AND yr IS NOT NULL;

EDA is about asking good questions and letting the data answer them honestly. Here are the threads I pulled — and what came back.

Which companies had the most layoffs overall?

Amazon led the dataset at 18,150 layoffs — followed by Google (12,000), Meta (11,000), Salesforce (10,090), and Microsoft (10,000). Big tech dominated the raw numbers. But these are absolute counts — the percentage stories are often more revealing.

→ Amazon alone accounts for ~4.7% of all layoffs in the dataset
Which companies laid off their entire workforce?

116 companies in this dataset reported 100% layoffs — meaning they effectively shut down. That's not a layoff round. That's a full collapse. Filtering for percentage_laid_off = 1 surfaces some wild names: Quibi ($2B raised, 0 employees left), Britishvolt, Deliveroo Australia, Zulily.

Full shutdowns query
SELECT * FROM layoffs_staging2
WHERE percentage_laid_off = 1
ORDER BY funds_raised_millions DESC;
How do layoffs look over time — monthly rolling total?

This is where window functions get interesting. A rolling 3-month SUM shows the momentum behind the numbers — not just individual spikes, but waves. The 2022 wave wasn't one event. It was months of sustained cuts across different sectors.

Rolling monthly total
WITH monthly AS (
  SELECT DATE_FORMAT(`date`,'%Y-%m') AS mth,
    SUM(total_laid_off) AS monthly_total
  FROM layoffs_staging2
  GROUP BY mth
)
SELECT mth, monthly_total,
  SUM(monthly_total) OVER (ORDER BY mth) AS rolling_total
FROM monthly;

The problem

Before this dashboard, getting a network-wide view of lab performance meant calling each site individually and assembling spreadsheets by hand. Nine sites. Six departments. No central view. Managers couldn't see which sites were struggling until it was already affecting output — and by then, it had already been affecting patients.

Site F had both the lowest TAT percentage and the worst staffing gap (−13 people). That connection wasn't visible until the data was in one place.
2

The approach: one file, two sheets, zero macros

The architecture is simple: a raw data sheet and a dashboard sheet linked entirely through SUMIFS and AVERAGEIFS. Change the month or site filter — every number recalculates. No macros. No VBA. Nothing that breaks when Excel updates or when IT installs a patch.

In a healthcare setting where IT support is limited and Excel literacy varies, robustness matters more than cleverness. Anything that requires a specialist to maintain is a liability.

3

What surfaced

Only Site C hit the 90% TAT target consistently. Sites F and I were both stuck below 85%. The staffing-TAT correlation — only visible once everything was aggregated — gave management something concrete to act on, not just a number to report upward and forget about.

The problem this solves

Real-world sales data is never perfectly complete. Dates get skipped. Systems go down. Records don't get logged. You end up with gaps — and gaps break time-series analysis, running totals, and trend comparisons.

I set up a sales table with intentional gaps (Jan 3 and Jan 6 missing), then built a solution step by step — from generating a complete date series using a recursive CTE, to joining it with actual data, to filling gaps using the values on either side of each hole.

2

Why LAG/LEAD beats the global average

Using the overall average (78) for every missing date ignores context completely. LAG and LEAD look at the actual values immediately before and after each gap. Jan 3's estimate uses Jan 2 (72) and Jan 4 (84) → 78. Jan 6's estimate uses Jan 5 (95) and Jan 7 (77) → 86.

That's 86, not 78. The difference matters because Jan 5 was a strong day — and the estimate for Jan 6 should reflect that momentum. The global average doesn't. Context-awareness is the whole point.

Each step in this project introduces exactly one new concept and builds on the last. The goal was to show progressive, structured thinking — not just the final query, but why every piece is there.
Actual vs estimated sales — Jan 1–7Jan 3 & 6 estimated via LAG/LEAD
Final query — LAG/LEAD interpolation
WITH RECURSIVE cte AS (
  SELECT CAST('2025-01-01' AS DATE) AS dt
  UNION ALL
  SELECT dt + INTERVAL 1 DAY FROM cte
  WHERE dt < CAST('2025-01-07' AS DATE)
)
SELECT cte.dt,
  COALESCE(s.num_sales,
    ROUND((
      LAG(s.num_sales) OVER(ORDER BY cte.dt) +
      LEAD(s.num_sales) OVER(ORDER BY cte.dt)
    ) / 2)
  ) AS sales_estimate
FROM cte
LEFT JOIN sales s ON cte.dt = s.dt;

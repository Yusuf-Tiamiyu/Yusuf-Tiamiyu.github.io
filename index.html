01

The Problem

Cerba Lancet Nigeria runs multiple diagnostic lab sites across Lagos. Every week, lab managers needed to know: are we meeting our 90% TAT target? Which sites are struggling? Which departments are the bottleneck? The answer was buried in Excel files, emailed back and forth, manually compiled. By the time anyone had a full picture, the week was already over.

Before this dashboard existed, a manager getting a network-wide view of lab performance had to call each site individually, collect spreadsheets, and stitch them together. Every. Single. Week.
02

The Approach

Build an upload-to-dashboard pipeline. Staff drop in their weekly Excel file → it gets parsed and pushed into a live MySQL database → everyone with a browser can immediately see the full picture. No email chains. No manual compilation. No waiting.

03

The Impact

Real-time visibility across the network. Sites that fall below 90% TAT are immediately visible — not days later when someone remembers to chase up a spreadsheet. Lab managers can spot trends week over week. Execs can see the whole network in one view.

This application is live in production. Real data. Real users. It runs on Railway with a persistent MySQL instance — always on, always current.
01

Upload & Parse

Staff upload the weekly Excel report through the app interface. pandas reads it, validates column structure, and rejects malformed files before they touch the database.

02

Write to MySQL

Parsed rows write to the MySQL database via SQLAlchemy. Each upload inserts new weekly records per site and department — nothing is overwritten, so the full history builds up over time.

03

Serve the Dashboard

Flask routes query the database and serve an interactive dashboard. Charts built with Chart.js show TAT% per site vs the 90% target, week-over-week trend lines, and department-level breakdowns.

04

Deploy on Railway

The full stack runs on Railway — Python app + persistent MySQL instance. Always-on, no manual server management, auto-deploys on push.

I came across this Kaggle dataset covering global tech layoffs from March 2020 to early 2023 — the full post-COVID arc. Hiring booms, then mass corrections. Companies that raised billions shutting down overnight. I wanted to see what the numbers actually looked like underneath all the headlines.

But the data was real-world messy: inconsistent date formats, blank industry fields, duplicates, trailing punctuation in country names. Before asking any questions, I had to make the data trustworthy.

I always clean first, explore second. Running analysis on dirty data gives you confidently wrong answers — and that's worse than no answer at all.

For the EDA, I went in without a fixed hypothesis. Just started pulling threads — which companies collapsed entirely? Which years were worst? Which industries got hit hardest? The data led.

Layoffs by Year — 2020 to 2023
01

Staging Table

Never touch raw data. Create a staging copy first — the original stays safe if anything goes wrong.

Setup
CREATE TABLE layoffs_staging LIKE layoffs;
INSERT INTO layoffs_staging SELECT * FROM layoffs;
02

Remove Duplicates with ROW_NUMBER()

Used ROW_NUMBER() partitioned across all key columns to flag exact duplicates. Anything with row_num > 1 is a copy — delete it.

Duplicate Removal
WITH dedup AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY company, location, industry,
    total_laid_off, percentage_laid_off, `date`,
    stage, country, funds_raised_millions
    ORDER BY company) AS row_num
  FROM layoffs_staging
)
DELETE FROM layoffs_staging2 WHERE row_num > 1;
03

Standardise: Crypto, Country Names, Dates

"Crypto", "Crypto Currency", "CryptoCurrency" — all the same thing. "United States." with a rogue period. Dates stored as text strings. Fixed them all.

Standardisation
UPDATE layoffs_staging2
SET industry = 'Crypto' WHERE industry LIKE 'Crypto%';

UPDATE layoffs_staging2
SET country = TRIM(TRAILING '.' FROM country);

-- Convert text dates to proper DATE type
UPDATE layoffs_staging2
SET `date` = STR_TO_DATE(`date`, '%m/%d/%Y');
04

Top 3 Per Year — DENSE_RANK + Double CTE

The most interesting query: rank companies by layoffs within each year to see who led the cuts year by year, not just overall.

EDA — Top 3 Per Year
WITH Company_Year AS (
  SELECT company, YEAR(`date`) AS yr,
    SUM(total_laid_off) AS total
  FROM layoffs_staging2
  GROUP BY company, yr
),
Ranked AS (
  SELECT *,
    DENSE_RANK() OVER (
      PARTITION BY yr
      ORDER BY total DESC) AS rank_num
  FROM Company_Year
)
SELECT * FROM Ranked
WHERE rank_num <= 3 AND yr IS NOT NULL
ORDER BY yr;

Actual vs Estimated Sales — Jan 1–7Jan 3 & Jan 6 estimated via LAG/LEAD
Why LAG/LEAD instead of just the average? Because the average ignores local trends. Jan 3 gets (72+84)/2 = 78. Jan 6 gets (95+77)/2 = 86. Context-aware, closer to reality.
Final Query — LAG/LEAD Interpolation
WITH RECURSIVE cte AS (
  SELECT CAST('2025-01-01' AS DATE) AS dt
  UNION ALL
  SELECT dt + INTERVAL 1 DAY FROM cte
  WHERE dt < CAST('2025-01-07' AS DATE)
)
SELECT cte.dt,
  COALESCE(
    s.num_sales,
    ROUND((
      LAG(s.num_sales) OVER(ORDER BY cte.dt) +
      LEAD(s.num_sales) OVER(ORDER BY cte.dt)
    ) / 2)
  ) AS sales_estimate
FROM cte
LEFT JOIN sales s ON cte.dt = s.dt;

Before this dashboard existed, getting a network-wide view of lab operations meant calling each site individually. Managers were asking things like "how many tests did Site F run last week?" and waiting on someone to go find a spreadsheet. Now they open one file.

The dashboard tracks Test Volume, TAT%, Analyzer Status, and Staffing — all updated by changing a week/month/site filter. Everything else recalculates automatically.

The real insight when this first went live: 52% staff adequacy across the network. Nearly half the departments were understaffed. That's not a number anyone had in front of them before — it was hidden inside individual site reports that nobody was aggregating.

Data without visibility is just storage. This dashboard made the invisible visible — and gave management something concrete to act on.

01

Data Architecture

Three sheets: DATA ENTRY (where weekly data gets added), PIVOT DATA (pre-computed all-time organisation totals), and DASHBOARD (what management sees). No manual copying between sheets — formulas handle everything.

02

Filter-Driven Calculations

A SELECTIONS sheet holds the current filter state (Year / Month / Week / Site / Department). Every KPI on the dashboard uses SUMIFS and AVERAGEIFS referencing those filter cells. Change the filter — every number updates instantly.

03

Staffing Gap Logic

Each site row in the data has required headcount vs actual. The dashboard calculates gap = actual - required, then flags anything with a negative gap as understaffed. The network-level 52% adequacy figure is an AVERAGEIFS across all sites.

The lab procurement team was managing 1,578 consumable items — gloves, reagents, pipettes, blood collection tubes — with no centralised system. Items were running out mid-month. Staff were discovering stockouts when they went to use something.

When the tracker went live for the first time, it flagged 1,414 of 1,578 items as below reorder level. 89.6%. That was a very interesting morning for the procurement team.

The tracker doesn't just show current stock. It calculates how many months of stock remain based on average monthly usage — so procurement can see not just "this is low" but "this will run out in 3 weeks."

Stock Status Distribution

A sample of items from the actual tracker — showing the auto-status logic in action:

The Status column is driven by a single formula: IF(C3<=D3,"REORDER NOW","OK"). The "Months of Stock" column divides current quantity by average monthly usage — so procurement knows exactly how urgent each item is.
01

Reorder Status Logic

The core formula: if current quantity is at or below the reorder level, flag it. Simple, but applied across 1,578 rows with conditional formatting, it turns the spreadsheet into a live alert system.

=IF(C3<=D3,"REORDER NOW","OK")
Reorder Level is set at 2× average monthly usage — a built-in 2-month safety buffer.
02

Months of Stock

Each item has an average monthly usage figure. Dividing current stock by that gives remaining months. IFERROR handles cases where usage is 0 to avoid divide-by-zero errors.

=IFERROR(C3/H3,0)
03

Monthly Summary Sheet

Change the month in one cell → the summary sheet recalculates total issuances, number of transactions, and most-issued-to department for every item. Powered by SUMIFS and COUNTIFS referencing the Issuance Log.

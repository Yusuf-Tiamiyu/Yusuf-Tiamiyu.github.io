Data Cleaning & EDA

Where it started

I came across this dataset on Kaggle — a record of tech company layoffs from 2020 all the way through early 2023. The timing made it interesting: this covers the entire post-COVID arc. Hiring booms, then mass corrections. Companies that raised billions shutting down overnight. I wanted to see what the numbers actually looked like underneath all the headlines.

But the data was messy. Real-world messy. Inconsistent date formats, blank industry fields, duplicate entries, trailing punctuation in country names. Before I could ask any questions, I had to make the data trustworthy. So I started there.

Dataset source: Kaggle — Layoffs 2022 by swaptr · 2,361 records across 9 columns · Companies from 50+ countries · Period: March 2020 – March 2023

My approach

I always clean first, explore second. Not because the rules say so, but because running analysis on dirty data gives you confidently wrong answers — and that’s worse than no answer at all.

For the cleaning, I followed a structured 4-step process I’ve built up over time. Then for the EDA, I went in without a specific question. I just started pulling threads that interested me — which companies collapsed entirely? Which years were the worst? Which industries got hit hardest? Let the data lead.

Key SQL concepts used: CTEs, Window Functions (ROW_NUMBER, DENSE_RANK), GROUP BY aggregations, Self-JOINs for null population, STR_TO_DATE, Rolling totals with SUM OVER, PARTITION BY ranking.

What I found

The scale was jarring. 386,379 jobs gone across 2,361 companies. Amazon alone cut 18,150 people. 116 companies laid off their entire workforce — Quibi, which raised $2 billion, was one of them. 2022 was by far the worst year, accounting for nearly half of all layoffs in the dataset. Consumer and Retail sectors were hit hardest. And the US wasn’t just the most represented country — it dominated, with 1,541 of the 2,361 entries.

First things first — I never touch raw data directly. I always create a staging table to work in, so the original is safe if anything goes wrong.
1

Create a staging table

Before doing anything, I copy the raw data into a staging table. This is my working copy — the original stays untouched. Good habit, saved me more than once.

setup — staging table 
-- Create a staging table that mirrors the raw data structure
CREATE TABLE layoffs_staging
LIKE layoffs;

-- Copy all raw data into the staging table
INSERT INTO layoffs_staging
SELECT *
FROM layoffs;

-- Verify it looks right
SELECT *
FROM layoffs_staging;
2

Remove duplicates

I used ROW_NUMBER() with a PARTITION BY across all key columns to flag duplicates. Then I created a second staging table with the row_num column included, so I could simply delete anything where row_num > 1. Clean and surgical.

step 1 — duplicate removal 
-- First, identify duplicates using ROW_NUMBER()
WITH dedup AS (
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY
            company, location, industry, total_laid_off,
            percentage_laid_off, `date`, stage, country, funds_raised_millions
        ORDER BY company) AS row_num
    FROM layoffs_staging
)
SELECT * FROM dedup WHERE row_num > 1;

-- Create a second staging table that includes the row_num column
CREATE TABLE layoffs_staging2 (
  `company`               text,
  `location`              text,
  `industry`              text,
  `total_laid_off`        int DEFAULT NULL,
  `percentage_laid_off`   text,
  `date`                  text,
  `stage`                 text,
  `country`               text,
  `funds_raised_millions` int DEFAULT NULL,
  `row_num`               INT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

-- Populate it with row numbers assigned
INSERT INTO layoffs_staging2
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY
            company, location, industry, total_laid_off,
            percentage_laid_off, `date`, stage, country, funds_raised_millions
        ORDER BY company) AS row_num
    FROM layoffs_staging;

-- Delete actual duplicates (row_num > 1 means it's a copy)
DELETE FROM layoffs_staging2
WHERE row_num > 1;
3

Standardise the data

This is where most of the messiness lives. Blank industry fields, "Crypto" written 3 different ways, "United States" vs "United States." with a rogue period, and dates stored as text strings. Fixed them all.

step 2 — standardisation 
-- Blank industry fields are harder to work with than NULLs, so convert them
UPDATE layoffs_staging2
SET industry = NULL
WHERE industry = '';

-- If another row exists for the same company with an industry filled in,
-- use that to populate the NULL rows. Smart way to avoid manual lookups.
UPDATE layoffs_staging2 t1
JOIN layoffs_staging2 t2 ON t1.company = t2.company
SET t1.industry = t2.industry
WHERE t1.industry IS NULL
AND t2.industry IS NOT NULL;

-- "Crypto", "Crypto Currency", "CryptoCurrency" -- all the same thing
UPDATE layoffs_staging2
SET industry = 'Crypto'
WHERE industry LIKE 'Crypto%';

-- "United States." -- yes, with a trailing period. Strip it.
UPDATE layoffs_staging2
SET country = TRIM(TRAILING '.' FROM country);

-- Dates were stored as text (e.g. "3/6/2023") -- convert to proper DATE type
UPDATE layoffs_staging2
SET `date` = STR_TO_DATE(`date`, '%m/%d/%Y');

ALTER TABLE layoffs_staging2
MODIFY COLUMN `date` DATE;
4

Remove rows we can’t use & clean up

Rows where both total_laid_off AND percentage_laid_off are NULL are useless for any analysis — we have no idea what happened. Delete them. Then drop the row_num helper column since it’s served its purpose.

step 3 — remove unusable rows 
-- If both layoff columns are null, the row gives us nothing useful
DELETE FROM layoffs_staging2
WHERE total_laid_off IS NULL
AND percentage_laid_off IS NULL;

-- Drop the row_num helper column -- job done, no longer needed
ALTER TABLE layoffs_staging2
DROP COLUMN row_num;

-- Final check -- clean data ready for analysis
SELECT *
FROM layoffs_staging2;
Note: I kept NULLs in total_laid_off, percentage_laid_off, and funds_raised_millions intentionally — they’re legitimately missing data, not errors, and NULL is more honest than filling them with zeros.
No brief, no hypothesis. I just went in and started asking questions. This is the part I genuinely enjoy — letting curiosity drive the queries.
What’s the scale of these layoffs?

Before anything else, I wanted to know the extremes. What was the single biggest layoff event? Did any company completely shut down?

scale — extremes
-- Largest single layoff event in the dataset
SELECT MAX(total_laid_off)
FROM layoffs_staging2;

-- Which company was it?
SELECT *
FROM layoffs_staging2
WHERE total_laid_off = 12000;

-- Companies that laid off 100% of their workforce (percentage = 1)
-- Ordered by total to see which were biggest before collapse
SELECT *
FROM layoffs_staging2
WHERE percentage_laid_off = 1
ORDER BY total_laid_off DESC;

-- Same, but ordered by funds raised -- see how big some of these companies were
SELECT *
FROM layoffs_staging2
WHERE percentage_laid_off = 1
ORDER BY funds_raised_millions DESC;
→ Google (12,000), Amazon (single event). Quibi raised $2B and shut down completely. 116 companies went to 0.
Which companies had the most total layoffs?

A company might appear multiple times in the dataset across different events. I wanted to sum them up and see who really cut the most people over the full period.

companies — total layoffs
-- Total layoffs per company (summed across all events)
SELECT company, SUM(total_laid_off) AS total_laid_off
FROM layoffs_staging2
GROUP BY company
ORDER BY 2 DESC
LIMIT 10;

-- Where were the layoffs happening geographically?
SELECT location, SUM(total_laid_off)
FROM layoffs_staging2
GROUP BY location
ORDER BY 2 DESC
LIMIT 5;

-- And by country?
SELECT country, SUM(total_laid_off)
FROM layoffs_staging2
GROUP BY country
ORDER BY 2 DESC
LIMIT 5;
→ Amazon (18,150), Google (12,000), Meta (11,000) — US dominated with 67% of all entries
How did layoffs trend across time — by year, and by industry?

I wanted to see the full arc. Was 2022 actually the worst? Which industries got wiped out? And at what stage of funding were companies laying off?

trends — time & industry
-- Total layoffs by year
SELECT YEAR(`date`), SUM(total_laid_off) AS total_laid_off
FROM layoffs_staging2
WHERE YEAR(`date`) IS NOT NULL
GROUP BY YEAR(`date`)
ORDER BY 1;

-- Which industries were hit hardest?
SELECT industry, SUM(total_laid_off)
FROM layoffs_staging2
GROUP BY industry
ORDER BY 2 DESC;

-- Layoffs by company funding stage -- were early stage or post-IPO companies cutting more?
SELECT stage, SUM(total_laid_off)
FROM layoffs_staging2
GROUP BY stage
ORDER BY 2 DESC;
→ 2022 was the worst year: 161,711 layoffs. Consumer & Retail sectors hit hardest. Post-IPO companies led all stages.
Per year, which companies were in the top 3 for layoffs?

This is where it gets interesting. I used a double CTE with DENSE_RANK() to rank companies within each year — so I could see who was leading the cuts year by year, not just overall.

advanced — top 3 per year (CTE + window function)
-- Step 1: Get each company's total layoffs per year
WITH Company_Year AS (
  SELECT company, YEAR(`date`) AS years, SUM(total_laid_off) AS total_laid_off
  FROM layoffs_staging2
  GROUP BY company, YEAR(`date`)
),

-- Step 2: Rank each company within its year
Company_Year_Rank AS (
  SELECT company, years, total_laid_off,
    DENSE_RANK() OVER (PARTITION BY years ORDER BY total_laid_off DESC) AS ranking
  FROM Company_Year
)

-- Step 3: Filter to top 3 per year
SELECT company, years, total_laid_off, ranking
FROM Company_Year_Rank
WHERE ranking <= 3
AND years IS NOT NULL
ORDER BY years ASC;
→ Uber dominated 2020, Bytedance in 2021, Meta/Amazon in 2022, Google/Microsoft in 2023
What does the rolling monthly total look like?

Monthly snapshots are useful, but a rolling total shows the cumulative weight of the crisis over time. I used a CTE to group by month, then ran SUM OVER on top of that to build the running total.

advanced — rolling total (CTE + SUM OVER)
-- Extract year-month, sum layoffs per month
WITH Date_CTE AS (
  SELECT
    SUBSTRING(`date`, 1, 7) AS month_date,
    SUM(total_laid_off) AS monthly_total
  FROM layoffs_staging2
  WHERE SUBSTRING(`date`, 1, 7) IS NOT NULL
  GROUP BY month_date
  ORDER BY month_date ASC
)

-- Now calculate the rolling (cumulative) total month by month
SELECT
  month_date,
  monthly_total,
  SUM(monthly_total) OVER (ORDER BY month_date ASC) AS rolling_total
FROM Date_CTE
ORDER BY month_date ASC;
→ Rolling total crossed 100,000 by mid-2022, hit 386,379 by early 2023 — the steepest climb was Nov 2022 – Jan 2023

★ Standout Findings
Quibi raised $2 billion and laid off 100% of its workforce. It was one of 116 companies that completely shut down in this period.
2021 was surprisingly quiet — only 15,823 layoffs. The post-COVID hiring boom was still in full swing. The correction hit hard in 2022.
Consumer industry led all sectors with 46,682 layoffs — a sign of how quickly pandemic-era demand evaporated as spending normalised.
The US accounted for 1,541 of 2,361 entries (65%) — not surprising given it’s the home of most major tech companies, but the concentration is stark.
Post-IPO companies led all funding stages in layoffs — meaning even established public companies weren’t immune. In some ways, they had more to cut.
Amazon’s 18,150 total makes it the single largest layer in the dataset — across multiple events, not just one. Big ship, but not immune to course corrections.

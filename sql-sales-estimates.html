The problem

Real-world sales data is never perfectly complete. Dates get skipped. Systems go down. Records don’t get logged. You end up with a table that has gaps — and gaps are a problem for any analysis that relies on trends, running totals, or time-series comparisons.

This project tackles that head-on. I set up a sales table with intentional gaps (January 3rd and 6th are missing), then built up a solution step by step — from generating a complete date series, to joining it with the real data, to intelligently filling in the missing values using the neighbouring actual figures either side of each gap.

Each step introduces a new SQL concept, and each concept builds on the last. By the end, you have a single query that takes a sparse, gappy dataset and returns a clean, complete, estimated series — all in pure SQL.

Why LAG and LEAD instead of just using the average?
Using the overall average (78) for every missing date ignores the trend. LAG and LEAD look at the actual values immediately before and after the gap, so the estimate reflects local context — Jan 3’s estimate of 78 uses Jan 2 (72) and Jan 4 (84), and Jan 6’s estimate of 86 uses Jan 5 (95) and Jan 7 (77). That’s smarter, and closer to what actually happened.
Why this matters for employers: This reflects more than just learning how to write SQL — it shows the ability to think with it: approaching problems progressively, maintaining awareness of data quality, and applying sound analytical judgment.

Set up the tables

CREATE TABLE INSERT INTO

Two tables: sales (with intentional gaps on Jan 3 and Jan 6) and final_sales (the complete target we’re working toward). The gap is deliberate — it’s the problem we’re solving.

setup
CREATE TABLE sales (dt DATE, num_sales INT);

INSERT INTO sales (dt, num_sales) VALUES
    ('2025-01-01', 61),
    ('2025-01-02', 72),
    ('2025-01-04', 84),  -- Jan 3 missing!
    ('2025-01-05', 95),
    ('2025-01-07', 77);  -- Jan 6 missing!
2

Generate a complete date series using UNION ALL

UNION / UNION ALL

Before we can fill the gaps, we need a complete list of dates to join against. The simple way: manually UNION each date. UNION removes duplicates; UNION ALL keeps everything — since our dates are all distinct, UNION ALL is the right choice here (and faster).

step 2 — generate dates
SELECT '2025-01-01' AS dt
UNION ALL
SELECT '2025-01-02'
UNION ALL
SELECT '2025-01-03'
UNION ALL
SELECT '2025-01-04'
UNION ALL
SELECT '2025-01-05'
UNION ALL
SELECT '2025-01-06'
UNION ALL
SELECT '2025-01-07';
3

Join the date series with real sales data

Subquery LEFT JOIN

Wrap the date series in a subquery, then LEFT JOIN the sales table onto it. LEFT JOIN is critical here — INNER JOIN would only return dates that exist in both tables, dropping our missing dates entirely. LEFT JOIN keeps all dates and returns NULL for the missing ones.

step 3 — subquery + left join
SELECT sq.dt, sales.num_sales
FROM (
    SELECT '2025-01-01' AS dt UNION ALL
    SELECT '2025-01-02'     UNION ALL
    SELECT '2025-01-03'     UNION ALL
    SELECT '2025-01-04'     UNION ALL
    SELECT '2025-01-05'     UNION ALL
    SELECT '2025-01-06'     UNION ALL
    SELECT '2025-01-07'
) AS sq
LEFT JOIN sales ON sq.dt = sales.dt;
-- Result: Jan 3 and Jan 6 appear with NULL num_sales
4

Refactor: subquery → CTE

CTE

Same query, cleaner structure. Move the date series into a CTE (Common Table Expression) so the main SELECT reads like plain English. CTEs don’t change what the query does — they change how readable and maintainable it is.

step 4 — CTE
WITH cte AS (
    SELECT '2025-01-01' AS dt UNION ALL
    SELECT '2025-01-02'         UNION ALL
    SELECT '2025-01-03'         UNION ALL
    SELECT '2025-01-04'         UNION ALL
    SELECT '2025-01-05'         UNION ALL
    SELECT '2025-01-06'         UNION ALL
    SELECT '2025-01-07'
)
SELECT cte.dt, sales.num_sales
FROM cte
LEFT JOIN sales ON cte.dt = sales.dt;
5

Upgrade to a Recursive CTE

Recursive CTE CAST Date Expressions

Hard-coding 7 dates is fine for a small range — but what if you needed 365? A Recursive CTE solves this elegantly. Start with Jan 1, then keep adding 1 day until you hit the end date. It generates the full series automatically, no matter how long the range.

step 5 — recursive CTE
WITH RECURSIVE cte AS (
    -- Anchor: starting date
    SELECT CAST('2025-01-01' AS DATE) AS dt

    UNION ALL

    -- Recursive: add 1 day until we reach the end
    SELECT dt + INTERVAL 1 DAY
    FROM cte
    WHERE dt < CAST('2025-01-07' AS DATE)
)
SELECT cte.dt, sales.num_sales
FROM cte
LEFT JOIN sales ON cte.dt = sales.dt;
6

Fill the NULLs — first attempt using average

COALESCE ROUND / AVG

COALESCE returns the first non-NULL value from a list. So: if num_sales is not NULL, use it. If it is NULL, fall back to the overall average. This gives us a complete series — though using a global average ignores local trends.

step 6 — coalesce + avg fallback
WITH RECURSIVE cte AS (
    SELECT CAST('2025-01-01' AS DATE) AS dt
    UNION ALL
    SELECT dt + INTERVAL 1 DAY FROM cte
    WHERE dt < CAST('2025-01-07' AS DATE)
)
SELECT cte.dt,
    COALESCE(
        sales.num_sales,
        ROUND((SELECT AVG(num_sales) FROM sales))
    ) AS sales_estimate
FROM cte
LEFT JOIN sales ON cte.dt = sales.dt;
-- Jan 3 → 78, Jan 6 → 78 (same average for both)
7

Explore window functions: ROW_NUMBER, LAG, LEAD

ROW_NUMBER LAG LEAD

Before using LAG and LEAD in the final query, I explored what they return on their own. ROW_NUMBER assigns a sequential position. LAG looks back at the previous row. LEAD looks ahead to the next row. Understanding their output is key before using them in calculations.

step 7 — window function exploration
SELECT
    dt,
    num_sales,
    ROW_NUMBER() OVER()         AS row_num,
    LAG(num_sales) OVER()      AS prior_row,
    LEAD(num_sales) OVER()     AS next_row
FROM sales;
8

Final query — smart interpolation with LAG & LEAD

LAG + LEAD COALESCE Recursive CTE

The complete solution. Instead of the global average, we use COALESCE to fall back to (LAG + LEAD) / 2 — the average of the values immediately before and after each gap. Jan 3 gets (72 + 84) / 2 = 78. Jan 6 gets (95 + 77) / 2 = 86. Context-aware, accurate, and entirely computed in SQL.

step 8 — final query
WITH RECURSIVE cte AS (
    SELECT CAST('2025-01-01' AS DATE) AS dt
    UNION ALL
    SELECT dt + INTERVAL 1 DAY FROM cte
    WHERE dt < CAST('2025-01-07' AS DATE)
)
SELECT
    cte.dt,
    COALESCE(
        sales.num_sales,
        ROUND((
            LAG(sales.num_sales)  OVER(ORDER BY cte.dt) +
            LEAD(sales.num_sales) OVER(ORDER BY cte.dt)
        ) / 2)
    ) AS sales_estimate
FROM cte
LEFT JOIN sales ON cte.dt = sales.dt;
-- Jan 3 → (72+84)/2 = 78 | Jan 6 → (95+77)/2 = 86
